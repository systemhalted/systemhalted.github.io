Java's =Stream.reduce= combines several values into one result, such as a total or a string. To understand when it works, we need three ideas:

1. /Associativity/: changing the grouping of operations leaves the result unchanged.
2. /Folding/: combining a collection into one result.
3. /Identity/: a value that leaves another value unchanged when combined with it.

Consider adding five integers:

#+begin_src java
import java.util.List;

List<Integer> nums = List.of(1, 2, 3, 4, 5);

int sum = nums.stream().reduce(0, Integer::sum); // 15
#+end_src

This one line replaces a loop that starts at zero and adds each number. It gives =15=, and switching to =parallelStream()= gives the same total. Addition can be regrouped without changing the result, and starting each partial sum at zero adds nothing extra.

Subtraction looks similar:

#+begin_src java
// Compiles, but violates the requirements of reduce.
int difference = nums.parallelStream()
        .reduce(0, (left, right) -> left - right);
#+end_src

Starting at zero and subtracting these numbers in order would give =-15=. But a parallel reduction can calculate partial results and combine them in a different grouping. With subtraction, that can change the answer. Zero also fails as an identity: =0 - 3= gives =-3=, not =3=.

Java's =reduce= depends on associativity and a suitable identity because it can combine partial results. Those requirements apply to sequential streams too.[fn:reduce]

** Folding and Java's =reduce=
:PROPERTIES:
:CUSTOM_ID: folding-what-reduce-really-does
:END:

A /left fold/ starts with a value, visits the elements in order, and combines each element with the running result. Adding our numbers from a starting value of zero gives:

#+begin_example
((((0 + 1) + 2) + 3) + 4) + 5
#+end_example

A left fold fixes the grouping. Its starting value can be any value the calculation requires.

The two argument version of =Stream.reduce= asks for something more specific: an identity and an associative combining function. It does not promise this particular grouping. The operation must work when applied to elements and when applied to partial results.

That distinction matters when a calculation depends on the previous result at every step. A loop lets us specify that sequence directly.

** Example 1: Integer addition
:PROPERTIES:
:CUSTOM_ID: example-1-integer-sum-the-happy-path
:END:

Using the same =nums= list:

#+begin_src java
int sequentialSum = nums.stream().reduce(0, Integer::sum);
int parallelSum = nums.parallelStream().reduce(0, Integer::sum);

System.out.println(sequentialSum); // 15
System.out.println(parallelSum);   // 15
#+end_src

Integer addition is associative: =(1 + 2) + 3= and =1 + (2 + 3)= both give =6=. Zero is its identity because adding zero on either side leaves the other number unchanged.

The stream can therefore sum =1, 2= to get =3=, sum =3, 4, 5= to get =12=, and add the partial results to get =15=. Each group can start at zero without changing the total. An empty stream returns zero.

Java's =int= addition remains associative under its defined overflow behavior. Overflow wraps the result; it does not make the grouping matter. Whether =int= has enough range for the calculation is a separate question.[fn:arithmetic]

** Example 2: Subtraction needs a specified sequence
:PROPERTIES:
:CUSTOM_ID: example-2-subtraction-with-reduce-same-shape-weird-result
:END:

Subtraction fails the associativity check:

#+begin_src java
System.out.println((1 - 2) - 3); // -4
System.out.println(1 - (2 - 3)); //  2
#+end_src

The operands stay in the same order. Only the grouping changes.

Zero also fails as an identity. Although =x - 0= equals =x=, =0 - x= generally does not. The subtraction call in the opening therefore violates both requirements.

A sequential run may appear to subtract every element from zero, but switching to =stream()= does not make subtraction a valid operation for =reduce=. There is no parallel subtraction result to promise here.

If the requirement is to start with =20= and subtract each number in list order, write that calculation:

#+begin_src java
int remaining = 20;

for (int number : nums) {
    remaining -= number;
}

System.out.println(remaining); // 5
#+end_src

Here, =20= is a starting amount. It does not need to be an identity.

** Example 3: An identity is not an extra starting amount
:PROPERTIES:
:CUSTOM_ID: example-3-wrong-identity-value-leads-to-skewed-output
:END:

Addition alone is not enough to make this valid:

#+begin_src java
// Invalid identity: adding 1 changes the other value.
int biased = nums.stream().reduce(1, Integer::sum);
#+end_src

A left fold starting at =1= would add one to the total. Reduction may introduce that value into several partial results.

For example, consider two groups. Starting each at =1= gives =1 + 1 + 2 = 4= and =1 + 3 + 4 + 5 = 13=. Combining them gives =17=, whereas adding one to the original total gives =16=. This illustrates the problem; it does not predict a particular parallel execution.

If an adjustment belongs in the calculation once, apply it once:

#+begin_src java
int adjusted = 1 + nums.parallelStream().reduce(0, Integer::sum);
System.out.println(adjusted); // 16
#+end_src

The identity depends on the operation: zero for addition, one for multiplication, and the empty string for concatenation.

** Example 4: String concatenation, grouping and order
:PROPERTIES:
:CUSTOM_ID: example-4-string-concatenation-grouping-versus-ordering
:END:

#+begin_src java
List<String> letters = List.of("a", "b", "c");

String sequentialText = letters.stream().reduce("", String::concat);
String parallelText = letters.parallelStream().reduce("", String::concat);

System.out.println(sequentialText); // abc
System.out.println(parallelText);   // abc
#+end_src

Concatenation is associative. Grouping the first two strings produces ="ab" + "c"=; grouping the last two produces ="a" + "bc"=. Both have the same content. The empty string leaves that content unchanged.

Changing order is different: ="a" + "b"= produces ="ab"=, while ="b" + "a"= produces ="ba"=. An operation that allows its operands to swap without changing the result is /commutative/. Concatenation is not commutative.

The list has a defined encounter order, which this reduction preserves in parallel. Both outputs are guaranteed to be =abc=. Calling =unordered()= removes the ordering requirement; it does not request a shuffle.[fn:ordering]

For ordinary text joining, =Collectors.joining()= expresses the same intent directly.[fn:collectors]

** Example 5: Floating point addition is not associative
:PROPERTIES:
:CUSTOM_ID: example-5-floating-point-sums-almost-associative
:END:

Changing the numeric type changes which rules hold:

#+begin_src java
double value = 1e16;

System.out.println((value + 1.0) + 1.0); // 1.0E16
System.out.println(value + (1.0 + 1.0)); // 1.0000000000000002E16
#+end_src

At this magnitude, adjacent =double= values are two apart. Each separate addition of =1.0= rounds back to =value=. Adding the two ones first produces =2.0=, which survives the final addition.

[[https://systemhalted.in/2025/12/04/ieee-754-doubles/][Part 1]] explains this rounding in detail. The consequence here is precise: floating point addition is not associative.[fn:arithmetic] =Double::sum= does not meet that requirement of =reduce=.

A fixed loop makes the evaluation order explicit, but it still rounds. Choose the calculation method according to the accuracy and reproducibility the application needs.

** Example 6: Counting words with =collect=
:PROPERTIES:
:CUSTOM_ID: example-6-merging-counts-in-maps-a-realistic-associative-operation
:END:

Word counts give a practical example of combining partial results. Merge two count maps by adding the count for each word. Grouping the merges differently leaves the counts unchanged, and an empty map contributes no counts.

We could write a reduction that creates a new map for every update, copying the existing counts each time. For this task, =collect= provides a simpler way to build and merge mutable maps:

#+begin_src java
import java.util.Map;
import java.util.stream.Collectors;

List<String> words = List.of("a", "b", "a", "c", "b", "a");

Map<String, Long> counts = words.parallelStream()
        .collect(Collectors.groupingBy(
                word -> word,
                Collectors.counting()));

System.out.println(counts.get("a")); // 3
System.out.println(counts.get("b")); // 2
System.out.println(counts.get("c")); // 1
#+end_src

=groupingBy= groups equal words, and =counting= counts the entries in each group.[fn:collectors] Reading each key avoids depending on the map's iteration order.

This collector is not concurrent. During parallel collection, partial maps are accumulated in isolation and combined after their accumulation finishes. Multiple threads do not update the same partial map simultaneously, so the maps need no additional synchronization for this collection.[fn:collector]

That isolation applies while collecting. The returned map is not guaranteed to be thread safe for later shared updates.[fn:collectors]

** Before using =reduce=
:PROPERTIES:
:CUSTOM_ID: a-mental-checklist-for-reduce
:END:

Check the operation on the Java values you actually use:

1. Can partial results be regrouped without changing the result?
2. Is the identity neutral for that operation?
3. Does the function leave the source unchanged and avoid depending on changing external state?
4. If order matters, does the stream retain the required encounter order?

Use a loop when the calculation requires a specific sequence. Use =collect= when building a mutable container.
