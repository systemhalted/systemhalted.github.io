At St. George's College in Agra, Computer Science became part of our curriculum in 1991, when I was in Class IV. We spent two years learning Logo before moving to BASIC in Class VI. I remember the version as GW-BASIC.

Drawing with Logo had given me a way to see what my commands did. In BASIC, I became more aware of the values held in variables and the order in which a program used them. Logo had variables and loops too.[fn:logo]

Consider a small program that calculates the perimeter of a square:

#+begin_src basic
10 INPUT "Enter side length"; S
20 P = 4 * S
30 PRINT "Perimeter = "; P
40 END
#+end_src

If you enter =5=, line 10 stores that value in =S=. Line 20 multiplies it by four and stores =20= in =P=. Line 30 prints the result, and line 40 ends the program.

There is something easy to overlook in =P = 4 * S=. On paper, that can express a relationship between a square's side and its perimeter. In this program, it is an assignment: calculate the expression using the current value of =S=, then store the result in =P=.[fn:assignment]

Suppose we add a line between the calculation and the output:

#+begin_src basic
25 S = 10
#+end_src

With the same input of =5=, the program still prints a perimeter of =20=. By the time it reaches =PRINT=, =S= contains =10=, but =P= still contains the result calculated earlier. Changing =S= does not cause line 20 to run again.

To get the perimeter for the new side length, we have to repeat the calculation after changing =S=.

In GW-BASIC, the numbers were part of how you entered and edited a program. Using =10=, =20=, =30=, and =40= left room for another line, such as =25=. You could enter that new line after the others, and GW-BASIC would store it in its numerical position.[fn:lines]

The placement of our new assignment changes the result. If we replace line 25 with =15 S = 10=, the program overwrites the entered value before calculating the perimeter. It now prints =40=, even if we enter =5=.

Both versions are valid BASIC. Neither produces a syntax error. To decide whether either is correct, we have to know what the program is supposed to do.

A short program makes this manageable. We can write down the value of each variable after each statement and compare it with what we expected. The point at which those values diverge gives us somewhere specific to investigate.

We can use the same calculation to print perimeters for side lengths from one to five:

#+begin_src basic
10 FOR S = 1 TO 5
20 P = 4 * S
30 PRINT S; P
40 NEXT S
50 END
#+end_src

On the first pass, =S= is =1= and =P= becomes =4=. On the second, =S= is =2= and =P= becomes =8=. =NEXT S= increments the counter and returns to the loop body while the counter remains within the specified range.[fn:loop]

The calculation has not changed. We have added a rule for how often to perform it and how the input changes between repetitions. Following the program now means keeping track of which pass we are on as well as which line is running.

For me, this was a useful part of learning BASIC: the programs were small enough to work through completely. When the result was wrong, I could go back through the statements and check the values. It is still a good place to start when debugging.
