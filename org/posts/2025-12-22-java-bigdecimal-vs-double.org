In [[/2025/12/04/ieee-754-doubles/][Part 1]], we saw why some decimal values cannot be represented exactly by a =double=. Java provides =BigDecimal= for calculations that need exact decimal values and explicit rounding rules.

Prices, rates and balances are common examples. But choosing =BigDecimal= is only the first step. We still need to decide how to create a value, when to round a calculation and what it means for two results to be equal.

We will start with how =BigDecimal= represents a number, then work through those decisions with Java examples.

** Unscaled value and scale
:PROPERTIES:
:CUSTOM_ID: bigdecimals-mental-model
:END:
A =BigDecimal= represents a number using an integer called the /unscaled value/ and another integer called the /scale/.[fn:representation]

#+begin_src java
import java.math.BigDecimal;

BigDecimal amount = new BigDecimal("123.45");

System.out.println(amount.unscaledValue()); // 12345
System.out.println(amount.scale());         // 2
#+end_src

The unscaled value contains the digits. The scale tells us how to interpret them:

=value = unscaledValue × 10^(-scale)=

Here, =12345 × 10^-2= gives us =123.45=. A scale of zero would give us =12345=.

For a nonnegative scale, we can think of it as the number of digits after the decimal point. A scale can also be negative: the same unscaled value with a scale of =-1= represents =123450=.

This representation lets =BigDecimal= store values such as =0.1= and =123.45= exactly. It can use more digits as needed, rather than fitting every value into the fixed precision of a =double=. That does not mean every calculation has an exact decimal answer. We will see that distinction when we get to division.

** Creating a BigDecimal
:PROPERTIES:
:CUSTOM_ID: never-construct-bigdecimal-from-a-double
:END:
These three expressions look similar, but they do not all create the same decimal value:

#+begin_src java
BigDecimal fromText = new BigDecimal("0.1");
BigDecimal fromDouble = new BigDecimal(0.1);
BigDecimal fromValueOf = BigDecimal.valueOf(0.1);

System.out.println(fromText);
// 0.1

System.out.println(fromDouble);
// 0.1000000000000000055511151231257827021181583404541015625

System.out.println(fromValueOf);
// 0.1
#+end_src

The string constructor reads ="0.1"= as a decimal value, giving us exactly one tenth.

The =double= constructor receives the binary approximation that Java uses for =0.1=. It converts that stored value to its exact decimal equivalent. The long result is useful if we want to inspect the actual value of a =double=. It is usually the wrong starting point if we intended to enter exactly one tenth.[fn:construction]

=BigDecimal.valueOf(double)= takes a different route. It obtains the decimal string produced by =Double.toString= and parses that string as a =BigDecimal=. For =0.1=, the string is ="0.1"=.

For a finite =double=, parsing its =Double.toString= output with =Double.parseDouble= gives us the same =double= again. That is a guarantee about converting a value to text and back. It does not recover the decimal input we originally intended.[fn:double-text]

For example, converting after an addition does not undo the rounding in that addition:

#+begin_src java
System.out.println(BigDecimal.valueOf(0.1 + 0.2));
// 0.30000000000000004
#+end_src

When the input is decimal text, such as ="123.45"= from a file, parse it directly as a =BigDecimal=. When it is an integer with a known scale, we can use both:

#+begin_src java
BigDecimal amountFromUnits = BigDecimal.valueOf(12345, 2);
System.out.println(amountFromUnits); // 123.45
#+end_src

If an API already supplies a =double=, =BigDecimal.valueOf= is useful, but it cannot restore information that was lost before the conversion. The choice depends on what the input represents and which value we need to preserve.

** Adding decimal amounts
:PROPERTIES:
:CUSTOM_ID: exact-sums-predictable-cents
:END:
We can see the difference between binary and decimal arithmetic by adding one tenth three times:

#+begin_src java
double binaryTotal = 0.0;
BigDecimal decimalTotal = BigDecimal.ZERO;
BigDecimal increment = new BigDecimal("0.10");

for (int i = 0; i < 3; i++) {
    binaryTotal += 0.1;
    decimalTotal = decimalTotal.add(increment);
}

System.out.println(binaryTotal);  // 0.30000000000000004
System.out.println(decimalTotal); // 0.30
#+end_src

The =BigDecimal= inputs are exact decimal values, and this version of =add= calculates an exact result. The result has scale =2=, inherited from the decimal amounts being added.

Notice that we assign the result of =add= back to =decimalTotal=. =BigDecimal= is immutable. Calling =decimalTotal.add(increment)= without using the returned value would leave =decimalTotal= unchanged.

These additions do not lose small amounts when the total grows. We can also regroup exact additions without changing their numerical result. If we supply a =MathContext= that rounds intermediate results, that last claim no longer holds in general. Rounding can make grouping matter again.

** Precision, scale and rounding
:PROPERTIES:
:CUSTOM_ID: scale-rounding-and-the-joy-of-being-explicit
:END:
An exact decimal representation of one third would need infinitely many digits. The division method below asks for an exact result, so it throws an exception:

#+begin_src java
BigDecimal.ONE.divide(BigDecimal.valueOf(3));
// Throws ArithmeticException
#+end_src

To accept an approximation, we must specify how to round it. This version asks for two digits after the decimal point:

#+begin_src java
import java.math.RoundingMode;

BigDecimal third = BigDecimal.ONE.divide(
    BigDecimal.valueOf(3), 2, RoundingMode.HALF_UP);

System.out.println(third); // 0.33
#+end_src

=HALF_UP= chooses the nearest permitted value. If the value is exactly halfway between two choices, it rounds away from zero. It is one available rule, not a default we should apply to every calculation. The required scale and rounding mode depend on what the result will be used for.[fn:rounding]

There are two different ways to specify the amount of precision we want: a limit on /significant digits/, or a number of /decimal places/. They give different results even when we use the same number:

#+begin_src java
import java.math.MathContext;

BigDecimal value = new BigDecimal("12.34567");

System.out.println(value.round(new MathContext(4, RoundingMode.HALF_UP)));
// 12.35

System.out.println(value.setScale(4, RoundingMode.HALF_UP));
// 12.3457
#+end_src

The =MathContext= limits the result to four significant digits, counting from the first nonzero digit. In =12.35=, the two digits before the decimal point count toward that limit. A context can also be supplied to arithmetic methods such as =add= and =divide=. It applies to the operation receiving it; it does not change a global setting.[fn:context]

=setScale(4, ...)= asks for four digits after the decimal point. In this example, it rounds the value to get there. Increasing the scale can instead add trailing zeros without changing the numerical value.

Both methods return a result. Neither changes =value=. Choose where to apply rounding as part of the calculation: rounding every intermediate amount and rounding only the final total can produce different answers.

** Comparing values
:PROPERTIES:
:CUSTOM_ID: equals-is-not-the-same-as-compareto
:END:
=BigDecimal= provides two useful meanings of equality:

#+begin_src java
BigDecimal x = new BigDecimal("1.0");
BigDecimal y = new BigDecimal("1.00");

System.out.println(x.equals(y));    // false
System.out.println(x.compareTo(y)); // 0
#+end_src

=equals= compares both the numerical value and the scale. The scales here are =1= and =2=, so the objects are not equal by that definition.

=compareTo= compares numerical values and returns zero when they are equal. Use =x.compareTo(y) == 0= when different scales should count as the same amount. Using =x == y= would compare their references, not their numerical values.[fn:equality]

The distinction also affects collections:

#+begin_src java
import java.util.HashSet;
import java.util.List;
import java.util.TreeSet;

System.out.println(new HashSet<>(List.of(x, y)).size()); // 2
System.out.println(new TreeSet<>(List.of(x, y)).size()); // 1
#+end_src

=HashSet= uses =equals= and =hashCode=, so it keeps both values. =TreeSet= with natural ordering uses =compareTo= to decide whether values are duplicates, so it keeps one.[fn:sets]

Decide whether scale is part of a value's meaning before using =BigDecimal= as a set element or a map key. If the application requires a common scale, apply that rule consistently and decide whether normalization is allowed to round. There is no universal scale or equality rule that suits every decimal calculation.
