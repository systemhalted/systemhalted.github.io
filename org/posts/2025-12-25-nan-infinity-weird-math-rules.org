** Why zero has a sign
:PROPERTIES:
:CUSTOM_ID: signed-zero-0.0
:END:
A nonzero result can be too small for a =double= to store. When a division rounds that result to zero, Java retains the result's sign. That sign can affect the result of a later division or angle calculation.

#+begin_src java
double positiveZero = Double.MIN_VALUE / 2.0;
double negativeZero = -Double.MIN_VALUE / 2.0;

System.out.println(positiveZero);                 // 0.0
System.out.println(negativeZero);                 // -0.0
System.out.println(positiveZero == negativeZero); // true
#+end_src

Each exact result has half the magnitude of =Double.MIN_VALUE=. Java cannot represent either result and rounds both to zero. The magnitude is lost, but the sign remains.

Both stored values have magnitude zero. The negative sign does not represent a hidden nonzero amount. The comparison =0.0 == -0.0= returns =true=, and =-0.0 < 0.0= returns =false=. An ordinary zero check, such as =denominator == 0.0=, catches both signs of zero.

The sign matters when the next operation uses it.

Consider the reciprocal, =1.0 / x=. Small positive inputs produce large positive results. Small negative inputs produce large negative results. Retaining the sign when an input rounds to zero preserves this distinction:

#+begin_src java
System.out.println(1.0 / positiveZero); // Infinity
System.out.println(1.0 / negativeZero); // -Infinity
#+end_src

If both inputs became positive zero, both divisions would produce positive infinity. The sign of the negative result would be lost. Signed zero preserves the sign of an intermediate result. It does not recover the magnitude lost through rounding. These are floating point rules; division by zero remains undefined in real arithmetic.

Signed zero also matters when calculating angles. =Math.atan2(y, x)= returns an angle in radians from =-pi= to =pi=. At the negative x axis, the sign of a zero =y= selects an endpoint of that range:

#+begin_src java
double angleAbove = Math.atan2(+0.0, -1.0);
double angleBelow = Math.atan2(-0.0, -1.0);

System.out.println(Math.toDegrees(angleAbove)); // 180.0
System.out.println(Math.toDegrees(angleBelow)); // -180.0
#+end_src

Points just above that axis have angles approaching =180= degrees. Points just below it have angles approaching =-180= degrees. The two endpoint angles describe the same geometric direction. Signed zero lets the method distinguish the two sides at the axis.

The endpoint distinction matters when an application needs to distinguish the two sides of this boundary. If it reports every angle in the range from =0= degrees inclusive to =360= degrees exclusive, both endpoints become =180= degrees. For that reported direction, the distinction is unnecessary.

The sign is part of the current value. It does not record the calculation's history: a program can also create =-0.0= directly. Signed zero alone does not track movement or count complete rotations.

** Infinity and overflow
:PROPERTIES:
:CUSTOM_ID: infinity-and
:END:
Java defines positive and negative infinity. Arithmetic can produce them through overflow or through division of a nonzero finite value by zero.

#+begin_src java
System.out.println(Double.MAX_VALUE * 2.0); // Infinity
System.out.println(1.0 / 0.0);              // Infinity
System.out.println(-1.0 / 0.0);             // -Infinity
#+end_src

A result that needs rounding can still remain finite. For example, =1.0 / 3.0= produces the finite approximation =0.3333333333333333=.

Positive infinity compares greater than every finite value. Negative infinity compares less than every finite value. Arithmetic involving infinity follows defined rules:

| Expression | Result |
|------------+--------|
| =Double.POSITIVE_INFINITY + 5.0= | =Infinity= |
| =Double.POSITIVE_INFINITY * -2.0= | =-Infinity= |
| =Double.POSITIVE_INFINITY + Double.NEGATIVE_INFINITY= | =NaN= |
| =Double.POSITIVE_INFINITY * 0.0= | =NaN= |
| =Double.POSITIVE_INFINITY / Double.POSITIVE_INFINITY= | =NaN= |

The last three operations produce =NaN=. Infinity does not make every arithmetic operation yield another infinity.

These division rules apply to floating point operands. Integer division by zero throws =ArithmeticException=. If one operand is a =double= and the other is an =int=, Java converts the integer operand and performs floating point division.

** NaN and invalid operations
:PROPERTIES:
:CUSTOM_ID: nan-not-a-number
:END:
Java uses =NaN= for results such as =0.0 / 0.0= and =Math.sqrt(-1.0)=.

An average with no observations provides a practical example:

#+begin_src java
double total = 0.0;
int count = 0;

double average = total / count;
System.out.println(average); // NaN
#+end_src

There is no average to report because the count is zero. A result of zero would instead report a numerical average. The =NaN= result lets the application distinguish these cases.

The division uses floating point arithmetic because =total= is a =double=. Java does not throw an arithmetic exception for this calculation.

Once a value is =NaN=, arithmetic operators such as =+= and =*= propagate it. Library methods can have exceptions to that behavior:

#+begin_src java
System.out.println(Double.NaN + 5.0);         // NaN
System.out.println(Double.NaN * 2.0);         // NaN
System.out.println(Math.pow(Double.NaN, 0.0)); // 1.0
#+end_src

The last result is part of the contract for =Math.pow=. A zero exponent produces =1.0=. Check a method's documented rules before assuming that it propagates =NaN=.

If either operand is =NaN=, the primitive equality test =a == b= returns =false=. The tests =a < b=, =a <= b=, =a > b= and =a >= b= also return =false=. The comparison =a != b= returns =true=.

#+begin_src java
double value = Double.NaN;

System.out.println(value == value);   // false
System.out.println(value != value);   // true
System.out.println(value < 5.0);      // false
System.out.println(value >= 5.0);     // false
System.out.println(Double.isNaN(value)); // true
#+end_src

Use =Double.isNaN(value)= when the question is whether a value is =NaN=. The expression =value == Double.NaN= always returns =false=.

These rules also affect range checks. If =value= is =NaN=, both parts of =value < 0.0 || value > 100.0= are false. A range check written that way does not reject =NaN=.

** Equality and ordering
:PROPERTIES:
:CUSTOM_ID: nan-and-sorting-two-different-worlds
:END:
Primitive comparisons do not define a total order over all =double= values. They leave =NaN= unordered.

Sorting needs an ordering that also handles =NaN= and signed zero. =Double.compare= supplies one. It orders negative zero before positive zero and places every =NaN= after positive infinity. It returns zero when both arguments are =NaN=.

=Arrays.sort(double[])= uses this ordering:

#+begin_src java
import java.util.Arrays;

double[] values = {
    3.0, Double.NaN, 0.0, -0.0, Double.POSITIVE_INFINITY
};

Arrays.sort(values);
System.out.println(Arrays.toString(values));
// [-0.0, 0.0, 3.0, Infinity, NaN]

System.out.println(values[3] <= values[4]);
// false

System.out.println(Double.compare(values[3], values[4]) <= 0);
// true
#+end_src

The array is sorted according to the documented ordering. The expression =a <= b= applies different rules when =NaN= is present. Use =Double.compare= when checking whether values follow this ordering.

=Arrays.binarySearch= uses a compatible ordering, but the array must already be sorted. The search does not rearrange it.

Boxed =Double= objects also have an =equals= method with rules that differ from the primitive comparison =a == b=.

In this table, boxed equality means =Double.valueOf(a).equals(Double.valueOf(b))=:

| Values =a= and =b= | Primitive =a == b= | Boxed =Double.equals= | =Double.compare(a, b)= |
|-------------------+---------------------+-----------------------+-----------------------|
| =NaN= and =NaN= | =false= | =true= | =0= |
| =-0.0= and =+0.0= | =true= | =false= | Less than zero |

The object equality and ordering rules agree with each other. They treat all NaNs as equal and distinguish the two signed zeros. Specify which operation you mean when discussing whether these values are equal.

This distinction affects collection keys. A =HashSet<Double>= uses the =equals= rules of =Double=, so it can contain both signed zeros:

#+begin_src java
import java.util.HashSet;

HashSet<Double> zeros = new HashSet<>();
zeros.add(0.0);
zeros.add(-0.0);

System.out.println(zeros.size()); // 2
#+end_src

Keep the sign while later numerical operations may use it. If an application treats both zeros as the same key, it can convert negative zero to positive zero:

#+begin_src java
double result = -0.0;
double normalized = result == 0.0 ? 0.0 : result;

System.out.println(normalized); // 0.0
#+end_src

This changes only exact zero values. Nonzero values remain unchanged, including very small negative values. Apply the same conversion before both insertion and lookup when the collection must treat the zeros as one key.

Java also prints negative zero as =-0.0=. The same conversion can remove that sign from output when the application does not need it. It does not address a nonzero negative value that a formatter rounds to a display such as =-0.00=. That is a separate display decision.

** Identifying values in Java
:PROPERTIES:
:CUSTOM_ID: practical-takeaways
:END:
Java provides three methods for checking these categories:

| Method | Returns =true= when |
|--------+----------------------|
| =Double.isNaN(value)= | The value is =NaN= |
| =Double.isInfinite(value)= | The value is positive or negative infinity |
| =Double.isFinite(value)= | The value is neither =NaN= nor infinity |

Finite values include both signed zeros and all subnormal values. An application must still check any other requirements. For example, =-5.0= is finite but fails a requirement for a positive duration.

These categories have distinct encodings. A =double= has a sign bit, an 11-bit exponent field and a 52-bit fraction field. The exponent field below is shown as an unsigned integer:

| Exponent field | Fraction bits | Meaning |
|----------------+---------------+---------|
| =0= | All zero | Positive or negative zero |
| =0= | At least one nonzero | Subnormal value |
| =1= through =2046= | Any | Normal value |
| =2047= | All zero | Positive or negative infinity |
| =2047= | At least one nonzero | =NaN= |

Use the classification methods for ordinary checks. They state the intent without requiring code to inspect the bit fields.
