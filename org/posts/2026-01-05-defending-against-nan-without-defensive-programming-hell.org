/This post is part of my [[https://systemhalted.in/categories/#cat-series-4-floating-point-without-tears][Floating Point Without Tears]] series on how Java represents numbers and performs calculations./

In [[/2025/12/25/nan-infinity-weird-math-rules/][Part 5]], we examined how Java produces and compares =NaN=, infinity and signed zero. This post looks at how an application should handle those values.

A calculation can produce a result that its caller cannot use. For example, a service that requires a finite ratio cannot accept infinity from an overflowing division. Replacing that result with zero would report a different numerical answer.

Before implementing a calculation, decide three things:

1. Which values does the method accept?
2. Which results does it promise to return?
3. How does it report a failure?

The examples below use Java 21. They show how to check these requirements and how to distinguish a calculated value from a failure.

** Decide which values are acceptable
:PROPERTIES:
:CUSTOM_ID: pattern-1-finite-by-default-as-a-guardrail
:END:
A finite =double= is neither =NaN= nor positive or negative infinity. =Double.isFinite(value)= checks this condition. Both signed zeros and all subnormal values are finite.

Finiteness is only one possible requirement. A duration may need to be positive. A percentage may need to be between zero and one hundred. A divisor may need to be nonzero. Each of these requirements needs its own check.

For example, =-1.0= is finite, but =Math.sqrt(-1.0)= returns =NaN=. Checking finiteness alone does not make that input acceptable.

Some APIs deliberately accept infinity, such as an API that uses positive infinity to represent an unbounded limit. That meaning must be part of the API's documented behavior. The methods in this post require finite inputs and finite results.

Finite results can still contain rounding error. The checks below establish the stated input and output requirements. They do not prove that a formula is correct or that its answer is sufficiently accurate.

** Check inputs and calculation results
:PROPERTIES:
:CUSTOM_ID: the-core-principle-validate-at-the-edges-compute-in-the-middle
:END:
Check incoming values where a component receives them. This may be a parser, a public method or the return from a library call. These are concrete examples of an input boundary.

A helper can reject =NaN= and both infinities:

#+begin_src java
static double requireFinite(double value, String name) {
    if (!Double.isFinite(value)) {
        throw new IllegalArgumentException(
            name + " must be finite, got " + value);
    }
    return value;
}
#+end_src

The helper names the rejected input in the exception message. It does not check the input's range or the result of a later calculation.

Consider a division method with these requirements: both inputs must be finite, the divisor must be nonzero, and the returned quotient must be finite.

#+begin_src java
static double divide(double numerator, double denominator) {
    requireFinite(numerator, "numerator");
    requireFinite(denominator, "denominator");

    if (denominator == 0.0) {
        throw new IllegalArgumentException(
            "denominator must not be zero");
    }

    double quotient = numerator / denominator;

    if (!Double.isFinite(quotient)) {
        throw new ArithmeticException(
            "division produced a non-finite result");
    }

    return quotient;
}
#+end_src

The first checks enforce the input requirements. The last check enforces the output requirement. An invalid argument produces =IllegalArgumentException=. A division that cannot produce a finite result produces =ArithmeticException=.

Here are three calls and their outcomes:

| Call | Outcome |
|------+---------|
| =divide(10.0, 2.0)= | Returns =5.0= |
| =divide(1.0, 0.0)= | Throws =IllegalArgumentException= |
| =divide(Double.MAX_VALUE, 0.5)= | Throws =ArithmeticException= |

In the last call, both inputs pass validation. The mathematical quotient is twice =Double.MAX_VALUE=, so the floating point division overflows to infinity. The result check detects that overflow.

The zero comparison rejects both =+0.0= and =-0.0=. This is a requirement of the method. Java's floating point division has defined results for zero divisors, as we saw in Part 5.

The method still permits rounding and results that underflow to zero. A requirement for a finite result does not imply exact arithmetic.

Place checks according to the conditions an operation can violate. A private method that receives values already checked against its requirements may not need the same input checks again. Its calculations can still require result checks.

This also applies to library calls. Check a method's documented input range and special cases. Arithmetic operators such as addition and multiplication propagate =NaN=, but library methods can define exceptions. For example, =Math.pow(Double.NaN, 0.0)= returns =1.0=.

** Return a value or a failure
:PROPERTIES:
:CUSTOM_ID: pattern-2-separate-invalid-from-zero-with-a-result-type
:END:
An exception is one way to report failure. A batch operation may instead need to record which calculation failed and continue with the next input.

A return type can represent either a calculated value or a failure reason. A sealed interface restricts the alternatives to the two record types declared here:

#+begin_src java
sealed interface CalcResult
        permits CalcResult.Value, CalcResult.Failure {

    record Value(double value) implements CalcResult {
        public Value {
            if (!Double.isFinite(value)) {
                throw new IllegalArgumentException(
                    "value must be finite");
            }
        }
    }

    record Failure(String reason) implements CalcResult {}
}
#+end_src

The =Value= constructor prevents a caller from storing =NaN= or infinity in that alternative. It guarantees finiteness, not every possible application requirement.

This version of division returns a =Failure= for each numerical condition it rejects:

#+begin_src java
static CalcResult divideResult(
        double numerator, double denominator) {

    if (!Double.isFinite(numerator)
            || !Double.isFinite(denominator)) {
        return new CalcResult.Failure("inputs must be finite");
    }

    if (denominator == 0.0) {
        return new CalcResult.Failure(
            "denominator must not be zero");
    }

    double quotient = numerator / denominator;

    if (!Double.isFinite(quotient)) {
        return new CalcResult.Failure(
            "division produced a non-finite result");
    }

    return new CalcResult.Value(quotient);
}
#+end_src

The quotient is checked before constructing =Value=. Without that check, an overflowing division would make the constructor throw, even though the method is meant to report this condition as a returned failure.

Both division methods enforce the same numerical requirements. They give callers different ways to handle failure.

A caller can use a pattern =switch= to handle the two alternatives:

#+begin_src java
CalcResult result = divideResult(Double.MAX_VALUE, 0.5);

switch (result) {
    case CalcResult.Value(double value) ->
        System.out.println("Result: " + value);
    case CalcResult.Failure(String reason) ->
        System.out.println("Failed: " + reason);
}
// Failed: division produced a non-finite result
#+end_src

The compiler checks that this =switch= covers the alternatives. The return type alone does not force a caller to inspect the result; a caller can still ignore it. The record patterns and pattern =switch= shown here are available without preview features in Java 21.

A calculated zero remains distinct from a failure. =divideResult(0.0, 2.0)= returns =Value= containing =0.0=. =divideResult(0.0, 0.0)= returns =Failure= because the divisor is zero.

** Choose a representation that fits the data
:PROPERTIES:
:CUSTOM_ID: pattern-3-domain-types-that-make-nan-impossible
:END:
Some values have requirements that a raw =double= does not express. Choose a representation that fits those requirements.

| Data | Possible representation | Requirements to define |
|------+-------------------------+------------------------|
| Count | =int= or =long= | Allowed range and behavior on overflow |
| Monetary amount | =BigDecimal= or a =long= count of a defined minor currency unit | Currency, decimal scale and rounding rules |
| Duration | =java.time.Duration= | Whether zero or negative durations are allowed and the permitted range |

These representations cannot store =NaN=. They do not remove all validation needs. An integer calculation can overflow. A decimal calculation can require rounding. A duration can be negative even when the application requires a positive value.

An immutable value class can check application requirements when it is constructed. For example, a percentage type can require a finite value between zero and one hundred. Code that receives an instance can then rely on those checked conditions.

The calculations that use such values still need to satisfy their own requirements. Choosing a type reduces the number of conditions that each caller must establish; it does not make every later calculation acceptable.

[[/2025/12/22/java-bigdecimal-vs-double/][Part 3]] discusses the choice between =BigDecimal= and =double= in more detail.

** Define what happens to rejected data
:PROPERTIES:
:CUSTOM_ID: pattern-5-centralize-sanitization-but-do-not-lie
:END:
When data does not meet the requirements, choose a response that has a defined meaning. Depending on the application, this may be rejecting the request, returning a failure, excluding an observation or using a documented default.

Consider three readings:

#+begin_example
2.0, 4.0, NaN
#+end_example

If the application permits excluding the =NaN= reading, the average of the two accepted readings is =3.0=. Replacing the rejected reading with zero gives an average of =2.0= across three readings.

Those procedures calculate different quantities. Excluding a reading changes which observations contribute to the average. Replacing it with zero adds a numerical value that was not observed.

If exclusions are permitted, identify the result as the average of the accepted readings. Report the accepted and rejected counts when the caller needs them to interpret the result. In this example, those counts are two and one.

If no readings remain, return a failure such as "no accepted readings". An existing numerical API may use =NaN= for that condition. A wrapper can translate that documented result into the application's failure representation.

Filtering inputs also does not prevent arithmetic overflow. Adding two values equal to =Double.MAX_VALUE= produces infinity, even though their mathematical average is representable. Use an aggregation method suited to the permitted input range and check that it produces an acceptable result.

Apply the chosen response consistently. Use zero as a replacement only when the application's requirements define zero as the correct value for that condition.

** Record enough information to find the cause
:PROPERTIES:
:CUSTOM_ID: finding-the-first-nan-not-the-last-one
:END:
When a value is rejected, retain the information needed to understand the failure: the operation, the rejected value, the reason, and a source or request identifier. For a failed calculation, the relevant operands can help explain the result.

The calculation can return a failure reason while its caller adds the request context. Record the failure at the point responsible for handling it. Repeated logging at every layer can produce several reports of the same event without adding useful information.

During development and testing, assertions can help identify an intermediate result that violates an assumption:

#+begin_src java
double partialTotal = Double.MAX_VALUE + Double.MAX_VALUE;

assert Double.isFinite(partialTotal)
    : "partialTotal became non-finite: " + partialTotal;
#+end_src

With assertions enabled, this code throws =AssertionError= because =partialTotal= is infinite. Enable Java assertions with =-ea=. When assertions are disabled, the assertion does not perform the check.

Use ordinary checks for requirements that must be enforced in production. Assertions are useful for checking assumptions during testing, but they can be disabled.

Test the method's failure behavior as well as its successful calculations. For the division examples, this includes =NaN=, both infinities, both signed zeros as divisors, and finite inputs whose quotient overflows. Also test a legitimate zero result so it remains distinguishable from a failure.
