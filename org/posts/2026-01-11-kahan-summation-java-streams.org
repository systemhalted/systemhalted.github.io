/This post is part of my [[https://systemhalted.in/categories/#cat-series-4-floating-point-without-tears][Floating Point Without Tears]] series on how Java represents numbers and performs calculations./

In [[/2026/01/05/defending-against-nan-without-defensive-programming-hell/][Part 6]], we defined which inputs and results a calculation accepts. We also saw that a finite result can still be inaccurate. Summation is one place where that distinction matters.

A program may need to add thousands of measurements, compute an average, or combine values from several batches. Each floating point addition can round its result. Depending on the values and their order, those rounding errors can change the final total enough to matter to the application.

This post explains three things:

1. How a running total can lose small contributions.
2. How Kahan summation uses a correction term to reduce that loss.
3. What Java's =DoubleStream.sum()= already provides and how to check the accuracy of a result.

The examples use Java 21. We will start with four values so that each step can be inspected.

** How a small contribution is lost
:PROPERTIES:
:CUSTOM_ID: a-quick-demo-sums-that-look-reasonable-and-are-still-wrong
:END:
Consider this sum:

#+begin_src java
double[] values = {1e16, 1.0, 1.0, -1e16};
double total = 0.0;

for (double value : values) {
    total += value;
}

System.out.println(total);             // 0.0
System.out.println(Math.ulp(1e16));   // 2.0
#+end_src

The mathematical total is =2.0=. The large positive and negative values cancel, leaving the two ones. The loop returns =0.0= because both ones are lost before the final subtraction.

At =1e16=, adjacent =double= values are separated by =2.0=. =Math.ulp= reports that spacing. The next representable value above =10000000000000000= is =10000000000000002=.

Adding =1.0= gives an exact result halfway between those values. Java [[https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.4][rounds a halfway result]] to the value whose binary significand ends in a zero bit. Here, it selects =10000000000000000=. The second addition of =1.0= repeats the same operation and produces the same result.

| Input | Running total after addition |
|-------+------------------------------|
| =1e16= | =10000000000000000= |
| =1.0= | =10000000000000000= |
| =1.0= | =10000000000000000= |
| =-1e16= | =0= |

The final subtraction exposes the earlier rounding loss. It is not the step where the two ones disappear.

The size of the total alone does not determine the error. Adding =2.0= to =1e16= is exact. The input values and their order determine which operations need rounding. The number of additions alone cannot tell us how many digits will be lost.

** How Kahan applies a correction
:PROPERTIES:
:CUSTOM_ID: kahan-summation-track-what-gets-dropped
:END:
Kahan summation is a form of /compensated summation/. It keeps two values:

- =sum= is the running total.
- =correction= estimates the rounding error from the previous addition, so it can be accounted for in the next input.

Start both values at zero. For each input =value=, perform these operations in order:

#+begin_src text
adjusted = value - correction
next = sum + adjusted
correction = (next - sum) - adjusted
sum = next
#+end_src

The expression =next - sum= measures the change that was stored. Subtracting =adjusted= compares that change with the value we tried to add. The subtraction operations can also round, so the correction is an estimate.

The sign matters. If we try to add =1.0= and the stored total does not change, the new correction is =0.0 - 1.0=, or =-1.0=. Subtracting that correction from the next input increases the next input by =1.0=.

Here is the same four-value example:

| Input | Adjusted input | New sum | New correction |
|-------+----------------+---------+----------------|
| =1e16= | =1e16= | =10000000000000000= | =0= |
| =1.0= | =1.0= | =10000000000000000= | =-1= |
| =1.0= | =2.0= | =10000000000000002= | =0= |
| =-1e16= | =-1e16= | =2= | =0= |

The first =1.0= does not change the total, but its effect is retained in the correction. The second =1.0= is adjusted to =2.0=, which can be added to the running total exactly. The final subtraction then leaves =2.0=.

This is why the correction helps in this example. It does not increase the precision of =double= or guarantee that every lost contribution can be recovered.

** A sequential Java implementation
:PROPERTIES:
:CUSTOM_ID: java-implementation-a-small-accumulator-with-big-consequences
:END:
This method processes an array in its existing order. It returns =0.0= for an empty array, rejects =NaN= and infinity as inputs, and throws if an intermediate calculation becomes nonfinite.

#+begin_src java
public final class Summation {
    private Summation() {}

    public static double kahanSum(double[] values) {
        double sum = 0.0;
        double correction = 0.0;

        for (double value : values) {
            if (!Double.isFinite(value)) {
                throw new IllegalArgumentException(
                    "All input values must be finite."
                );
            }

            double adjusted = value - correction;
            double next = sum + adjusted;
            double nextCorrection = (next - sum) - adjusted;

            if (!Double.isFinite(adjusted)
                    || !Double.isFinite(next)
                    || !Double.isFinite(nextCorrection)) {
                throw new ArithmeticException(
                    "A summation step produced a nonfinite result."
                );
            }

            sum = next;
            correction = nextCorrection;
        }

        return sum;
    }
}
#+end_src

Use it with the same inputs:

#+begin_src java
double[] values = {1e16, 1.0, 1.0, -1e16};
System.out.println(Summation.kahanSum(values)); // 2.0
#+end_src

The checks enforce the method's requirements. They do not establish numerical accuracy. For example, adding two =Double.MAX_VALUE= inputs causes an exception because an intermediate sum overflows. Compensation does not prevent that overflow, even if later inputs could reduce the mathematical total.

There is no merge operation in this implementation. Combining partial compensated sums is a separate algorithmic problem. Adding a =combine= method does not, by itself, make this sequential method suitable for parallel reduction.

** What Java's sum() already does
:PROPERTIES:
:CUSTOM_ID: using-it-with-streams
:END:
Java already provides a summation operation for primitive streams:

#+begin_src java
import java.util.stream.DoubleStream;

double total = DoubleStream.of(1e16, 1.0, 1.0, -1e16).sum();
System.out.println(total); // 2.0 on the OpenJDK 21 implementation used here
#+end_src

The [[https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/stream/DoubleStream.html#sum()][DoubleStream.sum() documentation]] permits compensated summation or another technique that reduces error. It does not specify one algorithm or one order of addition. The [[https://github.com/openjdk/jdk21u/blob/7a7090bd432d6e8b4e6106593957513a84e7add4/src/java.base/share/classes/java/util/stream/DoublePipeline.java#L441-L465][OpenJDK 21.0.13.1 implementation]] uses compensated summation; its [[https://github.com/openjdk/jdk21u/blob/7a7090bd432d6e8b4e6106593957513a84e7add4/src/java.base/share/classes/java/util/stream/Collectors.java#L717-L739][compensation helper]] performs the correction.

The custom method above makes the sequential calculation and its input policy visible. It is not evidence that a replacement for =DoubleStream.sum()= will be more accurate.

For an existing stream calculation, start by checking the behavior and accuracy of =sum()=. Its documented treatment of =NaN= and infinity differs from the exceptions used by our method. Apply the application's input and result requirements explicitly.

Parallel evaluation introduces another choice: how to group the values and combine partial totals. Different groupings can produce different answers because floating point addition is not associative. That does not mean every run of a parallel stream must return a different answer.

If results must be identical bit for bit, use a specified algorithm with a fixed input order and grouping. Calling =sequential()= [[https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/stream/BaseStream.html#sequential()][selects sequential execution]]. The =sum()= contract still leaves its addition order unspecified.

** How to check accuracy
:PROPERTIES:
:CUSTOM_ID: correctness-what-to-test-and-what-not-to-promise
:END:
First define the reference quantity. Are we testing the sum of the values already stored as =double=, or the sum of the original decimal inputs? Those can be different quantities.

For existing finite =double= inputs, =new BigDecimal(value)= captures each stored binary value exactly. Adding those values without a =MathContext= gives an exact reference sum for these examples. Decimal representation is not an obstacle: every finite binary floating point value has a finite decimal expansion.

The choice of constructor is deliberate. =BigDecimal.valueOf(value)= uses the value's decimal string representation. That conversion is useful for other purposes, but it can change the exact value used as the reference. The [[https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/math/BigDecimal.html#%3Cinit%3E(double)][BigDecimal constructor documentation]] explains this difference.

This example measures the absolute error of the returned =double=:

#+begin_src java
import java.math.BigDecimal;

public class SumAccuracyExample {
    public static void main(String[] args) {
        double[] values = {1e16, 1.0};
        BigDecimal exact = BigDecimal.ZERO;

        for (double value : values) {
            exact = exact.add(new BigDecimal(value));
        }

        double computed = Summation.kahanSum(values);
        BigDecimal error = new BigDecimal(computed)
            .subtract(exact)
            .abs();

        System.out.println("Exact: " + exact.toPlainString());
        System.out.println("Computed: " + computed);
        System.out.println("Absolute error: " + error.toPlainString());
    }
}
#+end_src

The output is:

#+begin_example
Exact: 10000000000000001
Computed: 1.0E16
Absolute error: 1
#+end_example

Here, the exact sum is not representable as a =double=. The returned value is correctly rounded, but it still differs from the mathematical sum by =1=.

If we converted =exact= to =double= before subtracting, the comparison would report zero. Such a comparison can test agreement with a correctly rounded reference. It does not measure the full mathematical error of the returned value.

Next, consider a sum whose exact result is representable but which Kahan still fails to produce:

#+begin_src java
double[] values = {1e16, 1.0, -1e16};
System.out.println(Summation.kahanSum(values)); // 0.0
#+end_src

The exact sum is =1.0=. After the addition of =1.0= is rounded away, the correction is =-1.0=. The next adjusted input tries to represent =-1e16 + 1.0=, which rounds back to =-1e16=. The correction is lost in that step, and the method returns zero.

All of these operations remain finite, so the validation checks do not detect the accuracy problem. This is why both kinds of checks are needed: tests of the method's accepted inputs and failures, and tests of its numerical error.

Useful test cases include an empty input, values of similar magnitude, values of very different magnitudes, positive and negative values that nearly cancel, and the nonfinite inputs and overflow that the method rejects. A fixed random dataset can supplement those cases. It cannot establish that one algorithm is more accurate for every possible input.

** Choosing a summation method
:PROPERTIES:
:CUSTOM_ID: when-to-use-what
:END:
Choose the representation and algorithm from the calculation's requirements.

If the quantities and rounding rules are defined in decimal, use a decimal representation such as =BigDecimal= from the original decimal input. Where appropriate, a fixed unit represented by an integer is another option. Kahan summation does not give =double= decimal arithmetic. [[/2025/12/22/java-bigdecimal-vs-double/][Part 3]] discusses that choice.

When =double= fits the data, measure the summation error against the accuracy the application needs. A short sum can lose important information, as the three-value example shows. A long sum can be exact for particular inputs. Dataset size alone is not enough to choose an algorithm.

Two other summation methods are useful to know:

- *Neumaier summation* changes how the correction is calculated according to which operand has the larger magnitude, then includes the accumulated correction in the final result. It returns =1.0= for the sequence =[1e16, 1.0, -1e16]= above. That result illustrates an advantage over Kahan for this sequence, not a guarantee of exactness for all inputs.
- *Pairwise summation* combines pairs of values, then pairs of partial sums, through a balanced tree. This reduces the longest chain of additions compared with a sequential running total. Pairwise grouping does not require similar magnitudes; sorting by magnitude is a separate choice.

The [[https://nhigham.com/wp-content/uploads/2023/10/high93s.pdf][analysis by Nicholas Higham]] compares summation methods and their error bounds. The accuracy depends on the inputs as well as the method.

Performance also needs measurement. The arithmetic in each Kahan step consists of one addition and three subtractions. The method in this post also performs validation. Compare implementations with the behavior the application requires, on representative data. There is no general percentage that describes the runtime cost across workloads.

Use a documented error tolerance to decide whether a result is acceptable. Specify ordering when reproducibility matters, and define how the calculation handles values outside its supported range. Compensation addresses accumulation error; those other requirements still need their own decisions.
