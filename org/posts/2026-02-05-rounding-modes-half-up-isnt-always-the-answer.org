In [[https://systemhalted.in/2026/01/11/kahan-summation-java-streams/][Part 7]], we examined how rounding during floating point addition can change a total. This post considers a related problem: a calculation produces more decimal places than its result is allowed to contain.

For example, a calculation may produce the exact decimal value =1.005=, but the result must have two decimal places. Both =1.00= and =1.01= are equally close. Using =BigDecimal= preserves the input exactly when it is read from a decimal string. It does not decide which result your application requires.

You need to specify three things:

1. *Scale:* how many decimal places the result must have.
2. *Rounding mode:* how to choose a result when the exact value does not fit that scale.
3. *Rounding stage:* when to apply the rule during the calculation.

These decisions are separate. Two calculations can use the same scale and rounding mode but produce different totals because they round at different stages.

** Decimal places and rounding modes
:PROPERTIES:
:CUSTOM_ID: rounding-modes
:END:
For a nonnegative scale, =BigDecimal= uses the scale to specify the number of decimal places. This example produces a value with two decimal places:

#+begin_src java
import java.math.BigDecimal;
import java.math.RoundingMode;

BigDecimal amount = new BigDecimal("1.005");
BigDecimal rounded = amount.setScale(2, RoundingMode.HALF_EVEN);
System.out.println(rounded); // 1.00
#+end_src

=setScale= returns a value; it does not modify =amount=. Here, =amount= remains =1.005=.

Scale is different from significant-digit precision. =setScale(2, mode)= asks for two decimal places. A =MathContext= with a precision of =2= limits a result to two significant digits, counted from its first nonzero digit. This post uses =setScale= because the examples require a fixed number of decimal places.

At scale =2=, =1.005= is a /tie/: it is halfway between =1.00= and =1.01=. Extra trailing zeros do not change that fact, so =1.00500= is also a tie. The value =1.0051= is above the halfway point and is closer to =1.01=.

Java's three nearest rounding modes, =HALF_UP=, =HALF_DOWN=, and =HALF_EVEN=, differ only in how they handle ties. The directed modes choose a direction even when the value is not a tie.

The following table rounds both inputs to two decimal places:

| Mode | Rule | =1.005= | =-1.005= |
|------+-------+---------+----------|
| =HALF_UP= | Nearest; ties away from zero | =1.01= | =-1.01= |
| =HALF_DOWN= | Nearest; ties toward zero | =1.00= | =-1.00= |
| =HALF_EVEN= | Nearest; ties to an even last retained digit | =1.00= | =-1.00= |
| =UP= | Away from zero | =1.01= | =-1.01= |
| =DOWN= | Toward zero | =1.00= | =-1.00= |
| =CEILING= | Toward positive infinity | =1.01= | =-1.00= |
| =FLOOR= | Toward negative infinity | =1.00= | =-1.01= |
| =UNNECESSARY= | Require an exact result at the requested scale | Exception | Exception |

If a value already fits the scale exactly, none of these modes changes its numerical value. For =1.0051=, all three nearest modes produce =1.01=, but =DOWN= and =FLOOR= produce =1.00=. =UNNECESSARY= throws =ArithmeticException= because an exact result at scale =2= is impossible.

The names =UP= and =DOWN= describe movement relative to zero. They do not mean larger and smaller on the number line. This matters for negative amounts: =HALF_UP= changes =-1.005= to =-1.01=, which is a smaller number with a greater magnitude.

** Start with the intended decimal value
:PROPERTIES:
:CUSTOM_ID: decimal-input
:END:
A rounding mode operates on the value it receives. If the value has already changed during conversion or arithmetic, selecting a different mode will not recover the original input.

Consider three ways to create a =BigDecimal=:

#+begin_src java
import java.math.BigDecimal;
import java.math.RoundingMode;

public class DecimalInputs {
  public static void main(String[] args) {
    BigDecimal fromDouble = new BigDecimal(1.005);
    BigDecimal fromText = new BigDecimal("1.005");
    BigDecimal fromCanonicalText = BigDecimal.valueOf(1.005);

    System.out.println(fromDouble);
    System.out.println(fromDouble.setScale(2, RoundingMode.HALF_UP));
    System.out.println(fromText.setScale(2, RoundingMode.HALF_UP));
    System.out.println(fromCanonicalText.setScale(2, RoundingMode.HALF_UP));
  }
}
#+end_src

The output is:

#+begin_src text
1.00499999999999989341858963598497211933135986328125
1.00
1.01
1.01
#+end_src

The =double= literal =1.005= stores a binary value slightly below the exact decimal =1.005=. The =BigDecimal(double)= constructor preserves that binary value exactly. It therefore receives a value below the tie, which rounds to =1.00=.

The string constructor receives the exact decimal =1.005=. That value is a tie, so =HALF_UP= produces =1.01=.

=BigDecimal.valueOf(double)= is a static factory method. It uses the canonical string produced by =Double.toString(double)=. For this literal, that string is ="1.005"=, so the result matches the string constructor.

The double constructor is useful when the existing binary value is what you want to preserve. Part 7 used it for that reason when constructing an exact reference sum. For a decimal amount supplied as text, use that text directly instead of converting it through =double= first.

=valueOf= does not undo earlier arithmetic error. For example:

#+begin_src java
import java.math.BigDecimal;

System.out.println(BigDecimal.valueOf(0.1 + 0.2)); // 0.30000000000000004
#+end_src

The addition happens before =valueOf= is called. The factory converts the result it receives.

** What the bias example shows
:PROPERTIES:
:CUSTOM_ID: rounding-bias
:END:
Suppose ten positive amounts fall exactly on ties at two decimal places. Round each amount, then add the rounded results:

#+begin_src java
import java.math.BigDecimal;
import java.math.RoundingMode;

public class RoundingBias {
  public static void main(String[] args) {
    String[] inputs = {"1.005", "1.015", "1.025", "1.035", "1.045",
                       "1.055", "1.065", "1.075", "1.085", "1.095"};
    BigDecimal halfUpSum = BigDecimal.ZERO;
    BigDecimal halfEvenSum = BigDecimal.ZERO;
    BigDecimal exactSum = BigDecimal.ZERO;

    System.out.println("Value -> HALF_UP / HALF_EVEN");
    for (String input : inputs) {
      BigDecimal value = new BigDecimal(input);
      BigDecimal halfUp = value.setScale(2, RoundingMode.HALF_UP);
      BigDecimal halfEven = value.setScale(2, RoundingMode.HALF_EVEN);

      System.out.println(input + " -> " + halfUp + " / " + halfEven);
      halfUpSum = halfUpSum.add(halfUp);
      halfEvenSum = halfEvenSum.add(halfEven);
      exactSum = exactSum.add(value);
    }

    System.out.println("HALF_UP sum: " + halfUpSum);
    System.out.println("HALF_EVEN sum: " + halfEvenSum);
    System.out.println("Exact sum: " + exactSum);
  }
}
#+end_src

The output is:

#+begin_src text
Value -> HALF_UP / HALF_EVEN
1.005 -> 1.01 / 1.00
1.015 -> 1.02 / 1.02
1.025 -> 1.03 / 1.02
1.035 -> 1.04 / 1.04
1.045 -> 1.05 / 1.04
1.055 -> 1.06 / 1.06
1.065 -> 1.07 / 1.06
1.075 -> 1.08 / 1.08
1.085 -> 1.09 / 1.08
1.095 -> 1.10 / 1.10
HALF_UP sum: 10.55
HALF_EVEN sum: 10.50
Exact sum: 10.500
#+end_src

With =HALF_UP=, each positive tie gains =0.005=. Ten such changes add =0.05= to the total. Repeating this same set would repeat the same positive error. Negative ties move away from zero in the other direction, so a mixed set of positive and negative inputs needs its own analysis.

With =HALF_EVEN=, five values in this set round down and five round up. Each error has the same magnitude, so they cancel. The final total equals the exact sum for these inputs.

=HALF_EVEN= does not alternate between directions or remember the previous result. It examines each value independently. For example, ten copies of =1.005= all round to =1.00=. Their rounded total is =10.00=, while their exact sum is =10.050=.

The benefit of =HALF_EVEN= is that it does not resolve every positive tie upward. It can reduce systematic error when the inputs contain a suitable mix of ties, but it does not guarantee that errors cancel. The ten-value example demonstrates one balanced set. Other collections of values can produce different patterns of error.

Java also uses nearest rounding with ties to even for =double= addition, subtraction, multiplication, and division. Those operations round to binary floating point values. The examples here round decimal values to a specified number of decimal places.

** Decide when to round
:PROPERTIES:
:CUSTOM_ID: rounding-timing
:END:
Choosing a mode is only part of the calculation rule. You must also decide which intermediate results, if any, must be rounded.

Consider two invoice lines, each calculated as =1.005=. Assume that the required rounding mode is =HALF_UP= and that settled amounts use two decimal places. There are still two different calculations:

#+begin_src java
import java.math.BigDecimal;
import java.math.RoundingMode;

public class InvoiceRounding {
  public static void main(String[] args) {
    BigDecimal firstLine = new BigDecimal("1.005");
    BigDecimal secondLine = new BigDecimal("1.005");

    BigDecimal roundedLines = firstLine.setScale(2, RoundingMode.HALF_UP)
        .add(secondLine.setScale(2, RoundingMode.HALF_UP));
    BigDecimal roundedTotal = firstLine.add(secondLine)
        .setScale(2, RoundingMode.HALF_UP);

    System.out.println("Round each line: " + roundedLines);
    System.out.println("Round the total: " + roundedTotal);
  }
}
#+end_src

The output is:

#+begin_src text
Round each line: 2.02
Round the total: 2.01
#+end_src

Rounding each line gives =1.01 + 1.01 = 2.02=. Adding first gives =2.010=, which becomes =2.01= at scale =2=.

If the requirement says that each line must become a settled amount in cents before addition, the first calculation follows that rule. If the requirement says to total the unrounded amounts and then round, the second follows it. The code needs to state which calculation is intended, and the tests need to check its result.

Keep exact intermediate results where possible until the specified rounding stage. Some operations, such as dividing =1= by =3=, require a separate precision or rounding rule because the exact result has a nonterminating decimal expansion. Any such intermediate rule is part of the calculation too.

Storing settled amounts as integer minor units is one option. It does not remove the rounding decision. An amount of =245= cents multiplied by =1.1= produces =269.5= cents, so returning to integer cents requires a rule. Rounding after every multiplication can still produce a different result from rounding once at the end.

** Reject values that would require rounding
:PROPERTIES:
:CUSTOM_ID: exact-scale
:END:
Sometimes the requirement is to accept only amounts that can be represented exactly in cents. In that case, rounding the input would hide a value that should have been rejected. Use =UNNECESSARY= to enforce the requirement:

#+begin_src java
import java.math.BigDecimal;
import java.math.RoundingMode;

BigDecimal accepted = new BigDecimal("1.230")
    .setScale(2, RoundingMode.UNNECESSARY); // 1.23

BigDecimal rejected = new BigDecimal("1.234")
    .setScale(2, RoundingMode.UNNECESSARY); // throws ArithmeticException
#+end_src

Removing the trailing zero from =1.230= does not change the value. Converting =1.234= to scale =2= would change it, so the second call throws.

The rule checks the numerical value. It does not require the input text to contain exactly two decimal digits:

| Input text | Result of =setScale(2, UNNECESSARY)= |
|------------+-------------------------------------|
| ="1"= | =1.00= |
| ="1.2"= | =1.20= |
| ="1.230"= | =1.23= |
| ="1.234"= | =ArithmeticException= |

The single-argument call =setScale(2)= also throws if changing the scale would require rounding. Use the explicit mode when it helps make the exactness requirement visible to the reader.

For each calculation, specify the input representation, result scale, rounding mode, and rounding stage. Use examples with ties, negative values, and multiple amounts to check that the implementation follows those requirements.
